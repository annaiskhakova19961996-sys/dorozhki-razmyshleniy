# Вход по почте и защита данных

Статус: архитектурный план. Авторизация, облачное хранение и отправка писем ещё не реализованы. Нельзя считать текущий интерфейс защищённым личным кабинетом.

## Предлагаемое решение

Использовать управляемый сервис авторизации, например Supabase Auth, и вход по одноразовому коду на почту. Пользователю не нужен пароль приложения; пароль от почтового ящика приложение никогда не запрашивает. Для детского продукта разумно предусмотреть аккаунт родителя и отдельные детские профили без детских адресов почты и полных имён.

1. Браузер отправляет почту серверному endpoint по HTTPS.
2. Сервер проверяет формат, лимиты по IP и адресу и передаёт запрос Auth-провайдеру. Ответ не раскрывает, зарегистрирован ли адрес.
3. Пользователь получает ограниченный по сроку одноразовый код и вводит его в приложении. Ограничиваются число попыток и частота повторных писем.
4. Сервер проверяет код у провайдера и создаёт серверную сессию. Браузеру выдаётся случайный идентификатор в cookie `HttpOnly; Secure; SameSite=Lax`. Токены провайдера хранятся на сервере, не в localStorage и не в репозитории. Это отдельный backend-for-frontend, не стандартная клиентская Supabase-сессия.
5. При каждом запросе сервер проверяет сессию и права на профиль. Пользовательский JWT передаётся в базу для RLS. Привилегированный service-role ключ не применяется для обычных пользовательских запросов.
6. Выход отзывает серверную сессию и очищает cookie. Предусмотреть окончание срока, ротацию, отзыв всех сессий и удаление аккаунта.

## Разделение данных

Таблицы: профили с `owner_id`, результаты с `profile_id` и уникальным `lesson_id`, заметки с `profile_id`, активность по дате. Включить Row Level Security на всех пользовательских таблицах. Политики SELECT, INSERT, UPDATE, DELETE должны проверять владельца через `auth.uid()`; для UPDATE необходимы и USING, и WITH CHECK. Доступ к дочернему профилю проверяется по родительскому аккаунту, а не по присланному клиентом идентификатору.

Для родительских и детских режимов отдельно определить доступ к дневнику; не обещать ребёнку конфиденциальность, которую выбранные права не обеспечивают. Не публиковать адреса почты, заметки или реальные имена в рейтингах. Локальные заметки импортировать в аккаунт только по явному действию пользователя, особенно на общем устройстве.

## Условия перед включением входа

- Проект Auth/БД в выбранном регионе, почтовый отправитель, HTTPS-хостинг с серверными функциями и точный список разрешённых URL возврата.
- Секреты — только в секретном хранилище хостинга. Не в JavaScript, README, GitHub или логах.
- Защита изменяющих запросов от CSRF, проверка Origin, ограничения частоты и размера запросов. Нельзя кешировать ответы с сессиями на общем CDN.
- Экранирование пользовательского текста, CSP без произвольного выполнения скриптов, актуальные зависимости.
- Понятное описание хранения данных, удаления аккаунта, согласий и правил для детской аудитории. Требования зависят от стран запуска и возраста пользователей; их надо определить до запуска.
- Резервное копирование с проверкой восстановления и удаление персональных данных из логов.

## Обязательные проверки

- Пользователь A не может читать или менять данные B даже при подмене ID.
- Неавторизованные запросы не получают персональные данные.
- Повторное использование, истечение срока и подбор кода отклоняются.
- Выход и отзыв сессии закрывают доступ к API.
- Переключение аккаунтов не показывает данные предыдущего пользователя.
- XSS-текст в заметке отображается как текст; CSRF-запросы отклоняются.
- Почта доставляется, лимиты работают, ошибки не раскрывают наличие аккаунта.

Абсолютной защищённости обещать нельзя: безопасность зависит от реализации, конфигурации, проверок и сопровождения.
